# MCU C 架构设计与实现规范

## 目录与职责

```text
src/
├── product/
│   ├── app/
│   ├── assemble/       # 规模小时可用同级的 assemble.c
│   ├── service/
│   └── domain/         # 按需，产品独有的领域规则
├── components/
│   ├── device/
│   ├── domain/         # 按需，可独立复用的通用算法
│   └── infra/
└── platform/
```

| 归属 | 职责 |
|---|---|
| `product/app` | 编排产品任务，确定调用时机、跨服务数据流与跨任务操作顺序 |
| `product/assemble` | 选择具体实现，确定实例与共享关系，提供所需资源、绑定依赖并按依赖顺序调用模块的初始化入口 |
| `product/service` | 实现具体任务，持有任务状态，执行产品所需的外部操作 |
| `product/domain` | 表达产品独有的概念、规则、判定与状态转换 |
| `components/device` | 提供可复用的设备族接口、厂家驱动和协议实现，自行定义所需端口 |
| `components/domain` | 提供可脱离产品、设备和平台独立运行的通用算法 |
| `components/infra` | 提供有独立职责的基础能力，例如时间运算和日志接口 |
| `platform` | 适配目标 MCU、SDK、板卡及运行环境，实现设备或基础组件要求的契约 |

`app`、`assemble`、`service` 同级，装配采用单文件还是目录由项目决定，两处 `domain` 按代码归属选择，只创建有内容的目录，简单产品规则可以先放在所属服务旁边

## 装配、服务与任务流

- 装配决定产品如何组成，各模块负责建立自己的内部状态，共享资源由掌握整体使用关系的一方决定何时初始化，模块内部的固定依赖可以直接使用，只有产品需要作出的选择才上收到装配入口
- 服务默认由外部驱动，声明调用时机、阻塞行为和执行上下文要求，由 `app` 选择具体调度方式，服务按职责提供入口，不强制每个服务都有 `init()` 和 `process()`
- 跨服务数据流由 `app` 显式编排，生产服务发布结果，`app` 将消费服务所需的数据作为输入传入，小值可以按值传递，较大数据优先使用只读视图，明确视图属于哪一次发布以及它在消费期间有效多久
- 单实例服务可以在自己的 `.c` 中使用私有 `static` 状态，需要多实例或隔离运行上下文时使用显式实例，不要求 `assemble` 统一持有服务状态
- 服务可以直接依赖语义合适的设备公共接口，如果完成条件、数据含义或操作粒度不同，再由服务定义窄接口并进行适配

## 通用算法与产品规则

**`components/domain` 采用沙盒式输入输出**

输入、配置和旧状态只读，所需时间显式传入，可以按值返回，也可以写入调用者明确指定的 `out` 或 `next_state`，这些输出不得与输入或旧状态共用同一块内存，算法不得修改其他外部状态或执行外部 I/O，跨轮计算由调用者提供旧状态，并决定何时采用下一状态

**`product/domain` 可以维护自身的领域状态**

允许读取固定产品规则，允许原地更新显式传入的领域实例，状态修改限于该实例自身，另可通过约定的输出交付结果，时钟、当前配置、其他模块的结果等外部可变事实由调用方显式提供，产品领域可以使用通用算法

领域结果可以表达判定、状态转换或产品规则要求的动作意图，简单意图用枚举或结果字段即可，`service` 负责实际执行，执行结果决定动作是否完成，跨任务执行顺序由 `app` 决定

## 设备族、实例与端口

- 设备族默认对上提供命名清晰的统一 `Interface`，即使首版只有一个厂家后端也可以采用，设备族定义公共操作、数据含义、单位及结果语义，具体驱动、厂家专有操作、协议编解码和内部算法默认使用普通 C 函数
- 设备自行声明对下所需的最小 `PortOps`，`platform` 适配设备，`assemble` 在需要时选择并绑定实现，设备代码及其契约应可脱离具体平台头文件独立编译，多个后端可以履行同一份由设备族拥有的契约，语义一致时平台可以复用实现
- 按需要用显式实例、句柄或逻辑 ID 指定设备，一个统一入口可以连接多个独立实例，同一固件也可使用不同厂家的实现，注册表、厂家驱动表、能力查询和组操作分别按真实需求采用
- 可以在构建时选定后端，也可以由 `assemble` 在初始化时绑定，默认在实例生命周期内保持固定，只有产品明确需要在线切换时，才定义切换接口及在途操作、回调归属、状态交接规则

## 执行结果与任务连续性

用模块自身的语义表达本次操作的实际结果，简单情况使用普通返回值，调用者确实需要区分多种结果时，再定义模块自己的状态类型，调度者依据已确认的任务规则决定后续行为

禁止自行引入安全机制，禁止防御性编程，尤其禁止因推测的风险随意打断任务流，发现潜在安全隐患时，向用户说明具体触发条件和可能影响，询问是否引入安全机制，是否引入及具体做法均由用户决定

只要任务能进行就继续，单项操作未完成时如实反馈其结果，继续推进仍具备条件的工作，某一步确实无法执行时，说明具体阻塞点，保留其他任务继续执行的能力

已有约定足以作出选择时直接采用，遇到尚未确认且会实质改变依赖、行为或协作方式的取舍时，说明差异并询问用户

## X-Macro、契约文档与 C 文件模板

- X-Macro 与 `Interface` 独立决定，同一组稳定条目需要派生枚举、名称映射等多种表示时，默认使用 X-Macro，一张普通 `static const` 表已经能做到只维护一次时，使用普通表，各项的具体行为留在普通函数中
- 用 Doxygen 把公共契约写在 `.h` 的声明旁，普通函数的契约紧靠函数声明，接口与端口回调的契约写在对应成员旁，按需说明单位、返回值、完成条件、缓冲区所有权与寿命、阻塞行为及调用上下文，`.c` 中按需解释实现原因
- 中文回复、文档及代码中的中文注释禁用中文句号，每段末尾不加标点，代码、命令和 snippets 保留必要的语法符号
- 创建 C 头文件或源文件时，使用随附的 [C snippets](assets/c.json)，分别对应 `header` 与 `source`，展开时以实际文件基本名替换 `${TM_FILENAME_BASE}`
- 基础 `source` 模板依次保留「变量声明」「私有函数声明」「接口函数实现」「私有函数实现」四个分区，只有该 `.c` 确实定义对外导出的接口对象时，才在「私有函数声明」之后、「接口函数实现」之前按模板样式增加以下分区

```c
// ! ========================= 接 口 变 量 定 义 ========================= ! //
```
